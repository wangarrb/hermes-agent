# 会话块切分设计 v1（2026-10-17）

状态：草案，待用户 review。用户已裁定核心方向：大拆、整合按会话、反思按 daily、forward-only。

## 1. 背景与问题

当前批 = 会话（1:1）。全库 379 批实测分布：

| 指标 | 值 |
|---|---|
| input_chars p50 | 2,304 |
| input_chars p90 | 15,105 |
| input_chars max | 59,872 |
| <2000 字符的批 | 156 / 379（41%） |
| 每批 LLM 调用 | ~2.8（实测 final9：196 calls / 70 batches） |

两个失衡：
- 小批（41%）：为微小内容付完整链固定开销（retain+整合+校验），约 40% 的调用数花在约 5% 的内容上
- 大批（max 60k 字符）：单批串行、重试面大、长尾拖整轮（"最慢批决定整轮"）

目标：批大小按内容量均衡——大拆（本 v1）、小合（二期）。

## 2. 设计原则（已裁定）

1. **扫描层零改动**：闭包 / 锚点 / 压缩后继均为会话级机制（sources.py），块切分发生在扫描之后，扫描层原样保留
2. **整合 = 会话级 scope**：块共享会话 scope，全部块事实齐后整合一次
3. **反思 / 摘要 = daily 级**：现状即跨会话聚合（`ReflectUnit(scope='daily')`），不改
4. **只动 retain 的交付单位**：会话当日 delta → 块
5. **forward-only**：存量 379 批（及各阶段状态）不动；新逻辑只作用于后续增量的新批

## 3. 切分规则（确定性，绝不按语义）

- 单位 = 会话的当日 delta（现有扫描产出，不变）
- 阈值：单批超过 **200 条消息**或 **50k 字符**（先到者为准）才切分
- 切分：按消息时间顺序定长切块（1..N → 块 1；N+1..2N → 块 2 …），每块 ≤ 阈值
- 日常 delta 通常远低于阈值（p90=15k 字符 < 50k）→ 绝大多数批不触发切分
- 参照既有大会话参考线（>200 条消息视为大会话），阈值取"较大"以压低触发面

## 4. 数据模型

- 块批记录（批 state）新增字段（向后兼容，存量批无此字段视为单块）：
  - `source_key`：会话锚（`{profile}:hermes:{sid}` 或 cutover 变体）
  - `chunk_index` / `chunk_count`：块序号与总数
- 作用域：`arrival-batch:<session_batch_id>`（会话级稳定 tag，替代当前的逐批 tag）——块共享
- 整合：会话 scope 内全部块的事实齐后触发一次（复用现有 scoped drain，scope 语义改会话级）
- 反思接线：`parent_batch_ids` 先做 块→会话 归并，再进 daily 聚合（聚合逻辑不变，只加映射层）

## 6. 测试方案

1. 单元：切分边界（正好=阈值 / 超 1 条 / 巨批多块 / 不触发）；块记录字段
2. 集成：块批走完整 retain→整合→反思链；会话级校验全绿（隔离层/回执/账本）
3. 回归：扫描套件全绿（零改动验证）；存量批状态零影响（forward-only 验证）
4. E2E：小规模真实运行，验证 scope / drain / 反思接线与调用数下降

## 7. 二期（暂不做，另行评估）

- 小会话组合（多源单批）：归因粒度与整合质量需单独验证
- 阈值调优：上线后按实际 delta 分布调整
- 期望收益（一期）：调用数降幅主要来自大批的并行化与长尾消除；小批组合的收益更大（-30~40% 调用）但风险也更大

## 8. 未决问题

- 阈值最终取值（200 条 / 50k 字符 vs 其他组合）
- scope tag 的命名与迁移（存量 scope 保留，新 scope 用会话级）
- 块批的 payload 是否含跨块上下文（建议不含——块间独立，整合层负责合并）
